Windows→iPhone public text was separately user-confirmed via the btleplug **central** path; iPhone→Windows was not separately confirmed. The `LinkWriter::BlueZ` variant name is misleading: the btleplug path is also built for Windows and is not literally BlueZ there.

`LinkWriter` is a small backend enum, not a general `Transport` interface: it exposes `connected`, a characteristic-value `write_limit`, `write`, and a host-only `wait_for_announcement`; inbound is always a btleplug `ValueNotification` stream, synthesized from an `mpsc` for raw ATT and WinRT. `chat` handles identity generation, frame sends, peer admission, UI, timers and link state in one function. `Receiver` knows UI output directly; `Options` knows phone-specific LE addresses. Backend-only ATT/GATT implementation is separated, but session, protocol, message and transport policies are not yet independent layers.

## actual signed-text paths

1. **iPhone → Linux**: stock iPhone peripheral sends notify on BitChat characteristic → either btleplug `prepare_link` notification stream or `DirectAtt` reader's `take_notifications` → `chat` select receive → `Receiver::receive` → `Packet::decode` and `Reassembler::accept` → signed `ANNOUNCE` binds sender to signing key → verify `MESSAGE`, dedup → `ui::Output::line`. On the paired phone's proven direct route, Linux supplies explicit address and LE-only L2CAP; no advertised service scan there.
2. **Linux → iPhone**: `chat` input → UTF-8 <=99-byte `Packet::new(MESSAGE)` → Ed25519 `sign` → `send` → `frames` → `LinkWriter::Direct` sends ATT Write Request and waits for ATT Write Response **or** `LinkWriter::BlueZ` uses btleplug GATT write → iPhone `BLEService+LinkLayerPeripheralRole.swift` → `BLEReceivePipeline.swift` → public message handler. ATT/GATT response is **not** a user delivery receipt.
3. **Linux → Windows**: Windows `GattHost::start` advertises desktop UUID (prior proven run used the stock UUID; current equivalent is `--stock-host`) → Linux opt-in `--desktop-peer` scans/connects/subscribes → same `chat` → `send`/`LinkWriter::BlueZ` characteristic write → WinRT `process_write` selects only the subscribed writer and feeds ordered `mpsc` → host `chat` → `Receiver::receive`/terminal. Source: `windows_gatt.rs` and `chatt3r.rs`.
4. **Windows → Linux**: WinRT waits for one subscriber and Linux signed announcement; `chat` receives and validates it, then queries per-session MTU → Windows `send` → `GattHost::write` targeted `NotifyValueForSubscribedClientAsync` → btleplug Linux notification stream → `Receiver::receive`/terminal. On new desktop UUID, user reported the exchange works with phone BT on, but no simultaneous direction-specific transcript was recorded. **Older stock-service** two-way exchange was explicitly user-confirmed with phone BT off.

## reuse and coupling risks (not change requests yet)

- packet header/signing/fragmentation were necessarily ported from upstream for compatibility, not invented. another local Python CLI independently implements `0x22`, signature and whole-packet fragmentation; reuse *ideas/vectors* rather than duplicate formats. legacy `src/main.rs` / `src/fragmentation.rs` etc. repeat **obsolete** packet semantics (`0x04` text) and should not be conflated with `--bin chatt3r`.
- `MAX_FRAME=16 KiB`, 256 fragments and `Receiver`'s whitelist explicitly discard `0x22`, compressed packets, Noise, and long packets: a file implementation needs different **per-type** bounds and upstream canonical compression/signature behavior; simply removing the 99-byte cap is unsafe.
- `send` commits individual BLE frames with fixed 20ms pacing and no application ACK; retrying an entire signed packet on reconnection could duplicate deliveries. `LinkWriter::connected` is not durable peer/session identity. WinRT routes writes using a subscriber count and OS device ID, not a validated signed per-link key; callback queue carries bytes without source/session metadata. multi-client must address this before generic session routing.
- host `wait_for_announcement`, scan service selection and MTU measurement are transport-specific decisions leaking into chat; `LinkWriter::BlueZ` misnames the shared btleplug Windows central. `Receiver` owns UI; `ValueNotification.uuid` is a BLE shape leaked into the shared inbound pipeline. Future socket transport needs byte/frame ingress plus link provenance, bounded capacities and send outcomes without pretending a write is delivered.
- desktop-only UUID prevents *stock-filtered* phone discovery; it is not access control. signing identity is ephemeral and announcer key continuity is in-memory only. Linux ATT `LE_PUBLIC`, manual address, GATT handle discovery and BlueZ bypass are phone-specific hacks; retain until an equally proven replacement works, don't auto-switch to them.
- a session/capability/transfer layer is **planned**, not shipped. separate stable identity, packet codec, peer/session state, link lifecycle, fragment recovery, and file persistence from transport-specific discovery/MTU/write; compare Android's existing multi-transport implementation before inventing control/data split. See [upstream reuse](upstream-reuse-audit.md), [file transfer](file-transfer-audit.md) and [Wi-Fi Aware](wifi-aware-audit.md).
