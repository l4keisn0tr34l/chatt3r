# wi-fi aware and fast direct transport audit — design only

No Wi-Fi Aware implementation or hardware test in chatt3r. Android source pin `permissionlesstech/bitchat-android` `1b8a8252` (GPL-3.0, **reference only**). Official Apple/Android/Microsoft documentation links below were checked for availability during this audit; support on this user's physical radios/OS versions was **not** checked. Wi-Fi Aware (NAN), Wi-Fi Direct/P2P and Apple's Multipeer Connectivity are different APIs/protocol families; none is automatically interoperable with the others.

## what official BitChat Android *actually* implements

| question | source-backed finding |
| --- | --- |
| discovery / identity | `wifi-aware/WifiAwareMeshService.kt:323-480` attaches `WifiAwareManager`, publishes and subscribes **the same service name `bitchat`**, advertises short peer ID as `serviceSpecificInfo`, maps session-scoped `PeerHandle` to provisional IDs, sends discovery-message pings and server-ready port. `:86` derives the 16-hex-char peer ID from `EncryptionService` fingerprint, aiming to match `BluetoothMeshService`. A provisional Wi-Fi route is rebound only after a validated *direct* signed ANNOUNCE (`:1209-1280`), not because advertising self-declared peer ID was trusted. `:1198` chooses initial socket server/client by peer ID order and has role-reversal retries; handles cannot be used across publish/subscribe sessions (`:126-133`). |
| data path | `:820-1132` builds `WifiAwareNetworkSpecifier`/`ConnectivityManager.requestNetwork`, binds IPv6 TCP `ServerSocket` and client `Socket` to the resulting `Network`; `wifi-aware/SyncedSocket.kt` frames whole BitChat bytes as BE u32 length + data, rejects frames >64 KiB and uses 90s read timeout. `mesh/MeshCore.kt`, `mesh/FragmentingPacketSender.kt` and `WifiAwareMeshService.kt:1613+` adapt the *same BitChat packet/Noise/fragment mesh concepts* to this socket transport. It is not a separate file-only bulk protocol. |
| transport selection | `mesh/UnifiedMeshService.kt:20-26,91-218`: when BLE is enabled, **public message and file broadcast choose BLE**; Wi-Fi Aware handles them only when BLE disabled. Directed messages/files prefer an already connected BLE peer with established Noise session; use Wi-Fi if BLE is not ready and Wi-Fi is ready; otherwise pick a connected/default transport and handshake there. This is not an automatic “large file → Wi-Fi” threshold or BLE-negotiated bulk offload. `startServices()` can start both independent radios. `sendBroadcastAnnounce()` runs on both. |
| bridging and duplicates | `service/TransportBridgeService.kt:20-245` registers `BLE`/`WIFI`, relays incoming packets to other registered transports with decremented TTL, a bounded 4096-entry 5-minute logical-packet SHA-256 dedup cache; direct paths go through transport mesh/packet processor's own dedup too. A local neighbor-only sync can be sent over both. This is more than two isolated chat windows, **but** cross-transport forwarding can produce copies, so source/TTL/dedup matter. |
| disappearance/fallback | `WifiAwareMeshService.kt:526-611,648-735,1286-1366` closes stale sockets, periodically reconnects from discovery, restarts terminated sessions through `WifiAwareController.kt`; `UnifiedMeshService` can choose BLE for **subsequent** sends when available. There is no evidenced seamless migration of the *same* live Noise session or an in-flight file to a new radio with byte-offset resume and exactly-once delivery; `getSessionState` checks separate BLE/Wi-Fi services. A failed write in a chosen transport is not proof that the other transport received that message. |
| files and throughput | `UnifiedMeshService:153-218` handles `BitchatFilePacket` through the same BLE/Wi-Fi send policy as messages; no file-only fast lane. Wi-Fi uses framed sockets, network-specific IPv6, role ordering, socket keepalives, timeout/restart and per-transport fragmentation (`FragmentingPacketSender`). Those are useful throughput-enabling primitives, but no measured transfer rate, automatic bulk selection or resumable arbitrary-file stream was found. `SyncedSocket` has a 64 KiB per-frame bound; file payload size is a separate limit. |

**Conclusion:** Android already does much of *multi-transport peer discovery, packet routing and fallback*; the proposed generic BLE+Wi-Fi diagram is **not novel**. Its architecture is **not** specifically “BLE discovery/control + Wi-Fi Aware data plane”: Aware independently discovers, connects, handshakes, carries public text and files, and bridges packets with BLE. Merely choosing Wi-Fi for large files and falling back for new sends would be an adaptation, not a new architecture. True cross-platform end-to-end transfer-session migration remains a separate unsolved requirement for chatt3r.

## platform feasibility under no internet/router/LAN/manual hotspot

| pair and transport | classification for **chatt3r today** | evidence and missing gate |
| --- | --- | --- |
| iPhone ↔ Linux, Wi-Fi Aware | **POSSIBLY SUPPORTED; REQUIRES CUSTOM APP; UNKNOWN / REQUIRES HARDWARE TEST** | Apple now provides `Wi-Fi Aware` framework on **iOS 26+** with publish/subscribe, pairing, service entitlement/Info.plist and Network.framework data paths; Apple's peer-to-peer sample uses two devices. Linux kernel `include/uapi/linux/nl80211.h` (local `/usr/include/linux/nl80211.h`: `NL80211_CMD_START_NAN`, `ADD_NAN_FUNCTION`) exposes NAN control, **not** a ready desktop application, driver capability or Apple pairing compatibility. Need actual Wi-Fi radio, driver, Linux NAN userspace, matching discovery/secure data path, custom iOS build and physical interop test. Stock BitChat iOS source inspected has no Aware transport. |
| iPhone ↔ Windows, Wi-Fi Aware | **UNKNOWN / REQUIRES HARDWARE TEST; REQUIRES CUSTOM APP** | Apple's iOS 26 framework is not a Windows API. Microsoft's published `Windows.Devices.WiFiDirect` is **Wi-Fi Direct**, not evidence of a Windows NAN publisher/data-path API interoperable with Apple's Aware; verify actual Windows OS/driver/API capability before promising it. Stock iOS BitChat is not a Wi-Fi Aware endpoint. |
| Linux ↔ Windows, Wi-Fi Aware | **UNKNOWN / REQUIRES HARDWARE TEST** | Linux nl80211 NAN command definitions don't prove driver/userspace support, and Windows Wi-Fi Direct docs don't prove NAN. Need a confirmed matching NAN API/device on each endpoint and interop test. No router/hotspot requirement can be met in principle by NAN, but no working implementation is established here. |
| Linux ↔ Windows, Wi-Fi Direct | **POSSIBLY SUPPORTED; UNKNOWN / REQUIRES HARDWARE TEST** | Microsoft documents a Wi-Fi Direct device/service API; Linux nl80211 P2P device commands exist. Discoverable hardware, OS APIs, common group formation/security and automatic app provisioning must be verified. A Wi-Fi Direct group owner is a protocol role, not a **manually created hotspot**; explicitly confirm whether any resulting network behavior fits the operator's constraint. No client code or test in chatt3r. |
| iPhone ↔ Linux / Windows, Wi-Fi Direct / Multipeer Connectivity | **NOT INTEROPERABLE as a drop-in assumption; REQUIRES CUSTOM APP for Apple's exposed direct options** | `MultipeerConnectivity` can use infrastructure Wi-Fi, peer-to-peer Wi-Fi and Bluetooth as system-selected paths, but does not document a generic interoperable Wi-Fi Direct/NAN protocol for arbitrary Linux/Windows peers. Apple's **Wi-Fi Aware** is the relevant newer standards-based candidate, *not* automatically equivalent to Multipeer Connectivity or AirDrop. Platform pair support is not proved without a custom iOS app and desktop peer implementation. |

Classifications deliberately separate **an OS/API possibility** from **this client supporting it**. No pair is currently `SUPPORTED` by chatt3r for fast direct transport, nor was any iPhone/desktop Wi-Fi Aware link demonstrated. iOS 26 availability depends on **installed OS, device capabilities and entitlement**; don't silently assume the user's iPhone supports it. Current iPhone↔Linux/Windows public text remains BLE.

## authoritative primary sources checked

- Apple [Wi-Fi Aware framework](https://developer.apple.com/documentation/wifiaware/) (iOS/iPadOS 26 availability, peer-to-peer without infrastructure, device pairing); [adopting Wi-Fi Aware](https://developer.apple.com/documentation/wifiaware/adopting-wi-fi-aware) (service declaration and entitlement); [building peer-to-peer apps](https://developer.apple.com/documentation/wifiaware/building-peer-to-peer-apps) (publisher, subscriber, physical-device sample); [Multipeer Connectivity](https://developer.apple.com/documentation/multipeerconnectivity).
- Android [Wi-Fi Aware overview](https://developer.android.com/develop/connectivity/wifi/wifi-aware), plus the pinned implementation files above. Android's platform feature does not prove iOS/Windows interop.
- Microsoft [Windows.Devices.WiFiDirect](https://learn.microsoft.com/en-us/uwp/api/windows.devices.wifidirect) and [WiFiDirect.Services](https://learn.microsoft.com/en-us/uwp/api/windows.devices.wifidirect.services) (the latter is marked deprecated); **neither** documents cross-platform NAN for chatt3r. Linux kernel's installed `nl80211.h` declares NAN and separately P2P commands; a header is not a hardware certification.

## feasible *future* architecture question, not a build plan

Retain BLE as a standalone working fallback. Add explicit per-link provenance, validated stable peer identity, negotiated capabilities and file-size limits, and a transfer state machine above *distinct* transports. Only if both peers have a tested interoperable fast direct API should a large file select that link; verify end-to-end content and report real receiver receipt, handle loss without replaying an ambiguous write, and only then consider resume. An optional fast socket can share the BitChat `0x22` envelope for small compatible files; multi-megabyte streaming/restart semantics cannot be asserted from `0x22` alone. This concept is **partly already present** in Android's UnifiedMeshService, not uniquely chatt3r. Hardware/OS research and the file baseline come before any implementation.
